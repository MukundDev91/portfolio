Healthcare · Enterprise Platform

Integrated Healthcare Technology Management

Jan 2024 — Present

A modular backend for hospital operations — inventory, purchasing, outpatient, and equipment tracking — rebuilt as independent microservices behind a shared authentication layer.

Problem

Inventory, procurement, OPD scheduling, and equipment (OEM) tracking ran as tightly coupled modules — slow under load and hard to change independently as usage scaled.

Context

A production hospital-technology platform used daily by clinical and administrative staff, where every endpoint needs enforced authentication and integration touchpoints need clear, documented contracts.

Architecture

6+ independent microservices (Inventory, Purchase, OPD, OEM, and supporting services) on ASP.NET Core and C#, each with its own Dapper-based data-access boundary, sitting behind a shared JWT authentication/authorization layer and consumed by an Angular 13+ front end. APIs documented and versioned with Swagger.

Implementation

I designed the services' domain logic and API contracts applying SOLID principles, implemented JWT authentication and role-based authorization across services, wrote and optimized the SQL Server queries and stored procedures behind the highest-traffic endpoints, and built the Angular components consuming these APIs in production — plus the shared global exception handling, logging, and Azure DevOps CI/CD pipeline.

Engineering Challenges

  • Splitting coupled functionality into independently deployable services without breaking existing integrations
  • Keeping query performance predictable on high-volume transactional tables as usage grew
  • Enforcing consistent auth behavior across every service boundary, not per endpoint

Trade-offs

Chose Dapper over EF Core on transaction-heavy endpoints — more SQL to write and maintain, in exchange for predictable query plans and lower ORM overhead. Centralized authentication adds a network hop per request, accepted for a single auditable access-control point instead of duplicated auth logic per service.

Performance

Service decomposition plus targeted query/stored-procedure optimization brought API response times down ~35% and data retrieval down 40%+ on the affected high-volume transactions.

Security

JWT-based authentication with role-based authorization enforced at the API layer, scoped so clinical and administrative users reach only the data and actions relevant to their role.

Outcome

A microservices backend serving 5,000+ daily active users across inventory, purchasing, OPD, and OEM workflows, with Swagger contracts letting other internal teams and third-party systems integrate without direct coordination.

Lessons

I'd introduce contract/integration tests between services earlier — relying mainly on manual QA across service boundaries got harder to sustain as the number of services grew.

Finance · Audit & Compliance

Financial Assurance Portal

Apr 2023 — Dec 2023

An audit and compliance portal with dynamic multi-step workflows and an AI-assisted reporting layer that turns raw audit data into summaries, risk insights, and visual reports.

Problem

Audit and compliance reporting was largely manual — auditors assembling findings, risk assessments, and summaries by hand across multi-step review workflows, slow and error-prone as record volumes grew.

Context

An enterprise finance/audit portal used by auditors and business stakeholders who need accurate, defensible reports; workflows vary by audit type, so the system had to model different multi-step processes without hardcoding each one.

Architecture

ASP.NET MVC application backed by SQL Server via EF Core, with a workflow engine modeled using OOP (polymorphism and inheritance) so new audit workflow types are added as new classes rather than new branching logic. An AI-assisted reporting layer calls OpenAI/GPT APIs for on-demand narrative summaries and risk insights, paired with JavaScript-built interactive heatmap visualizations.

Implementation

I built the multi-step workflow model and its OOP class hierarchy, the EF Core data layer and the indexed queries/stored procedures behind report generation, the GPT-API integration for AI-assisted summaries, the heatmap visualizations, and the validation, error-handling, and audit-trail logging needed for compliance readiness — plus branching, code review, and release management through TFS.

Engineering Challenges

  • Modeling genuinely different audit workflows through a shared polymorphic structure without the abstraction leaking
  • Keeping report generation fast and accurate over 10k+ records
  • Integrating a third-party AI API into a compliance-sensitive workflow without it becoming a single point of failure

Trade-offs

GPT-generated summaries are used as an assistive first draft auditors review and adjust, not an autonomous output — trading full automation for auditor trust and compliance defensibility. Report queries were optimized with targeted indexes and stored procedures rather than a broader data-warehouse rework, which fit the timeline but would need revisiting at much larger volumes.

Performance

Indexed queries and custom stored procedures kept report generation responsive across 10k+ records; the workflow and AI-assist changes together cut manual processing time ~40% and lifted auditor productivity ~25%.

Security

Validation, error handling, and audit-trail mechanisms built into the workflow to preserve data accuracy and support compliance review, with controlled, reviewed releases through TFS.

Outcome

Auditors moved from manual report assembly to a workflow-driven portal with AI-assisted drafting and interactive risk visualizations, reducing processing time and increasing throughput on large record sets.

Lessons

Given how much review time the GPT-assisted drafts saved, I'd push earlier for structured prompt templates and output validation around the AI integration, rather than refining that after the workflow engine was already in place.

Principles

How I think about engineering

01 / Performance

Measure before optimizing.

Guesswork on what's slow wastes more time than the optimization itself.

02 / Maintainability

Prefer simple designs that teams can understand and change.

Clever code that only the author understands is a liability, not an asset.

03 / Security

Design auth in — don't bolt it on.

Authentication and authorization should be part of the system's shape from the start.

04 / Reliability

Plan for predictable failure.

Production systems need predictable failure handling, logging, and observability.

05 / Data

The database is part of the application.

Schema design and query performance are engineering work, not an afterthought.

06 / Architecture

Complexity has to earn its place.

Use it when it solves a real problem — not because a diagram looks impressive.

Writing

Field notes.

Short, practical takeaways from production work — not filler posts.

API Design

Designing REST APIs in ASP.NET Core

Resource-oriented routes, consistent status codes, and versioning decided up front save the most pain later. I document contracts with Swagger before a third-party team ever integrates, keep controllers thin, and treat a consistent error-response shape as a feature, not a nice-to-have.

Data Access

Dapper vs Entity Framework Core

EF Core wins on developer velocity — CRUD-heavy screens, migrations, LINQ queries that don't need hand-tuning. Dapper earns its place where query plans and latency actually matter: high-volume reads, reporting over large tables. Mixing both is fine as long as the boundary is explicit.

Security

JWT Authentication & Role-Based Authorization

JWT gets authentication half right; the other half is deciding what a token's claims actually authorize once it reaches a service. I design roles as part of the API contract and centralize token validation so every service enforces access the same way.

Performance

SQL Query Optimization Techniques

Most query problems I've fixed came down to a missing or wrong index. Before touching a query, I read the actual execution plan — what's scanning instead of seeking, what's spilling to tempdb — and reserve stored procedures for the highest-traffic paths.

Architecture

Microservices: When They Help and When They Don't

Splitting the healthcare platform paid off because inventory, purchasing, OPD, and OEM genuinely had different change rates and owners. It's not free — you trade function calls for network calls and take on service-to-service auth as a first-class problem.

Reliability

Global Exception Handling in ASP.NET Core

One exception-handling middleware that maps exceptions to a consistent response, logs with enough context to debug from, and never leaks internal details to the client — cheap to add on day one, expensive to retrofit once every controller has its own try/catch.

About

Backend engineering, applied to systems that can't be wrong.

I build the backend systems enterprises run their operations on — not prototypes, systems already in front of thousands of daily users that can't afford to be wrong. Most of my work sits at the intersection of API design, database performance, and access control: turning business requirements into services that are fast under real load, secure by default, and structured so another engineer can extend them without unpicking a mess.

The two domains I've spent the most time in — healthcare and finance — both have low tolerance for sloppy engineering. Healthcare data access has to be scoped correctly every time; audit and compliance workflows have to produce numbers people are willing to sign off on. That's shaped how I approach new work: authentication and authorization designed in from the start, query performance treated as part of the feature, and enough logging and error handling that production issues are diagnosable instead of mysterious.

Day to day that means C# and ASP.NET Core on the backend, SQL Server tuned through Dapper or EF Core depending on what the endpoint needs, Angular where the API needs a front end, and Azure DevOps pipelines carrying it to production inside an Agile team. Increasingly it also means the conversations around that code — with clients on requirements, with the team on who's picking up what — covered in more detail under Leadership.
